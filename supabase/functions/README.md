# Edge Functions Iris

| Fonction | Rôle | `verify_jwt` | Auth | État |
|---|---|---|---|---|
| **`requests-api`** | **API d'ingestion générique multi-source** (enveloppe commune, idempotence, conflits, pièces par URL signée, OpenAPI `/v1/openapi.json`) — voir [`../../docs/api-ingestion.md`](../../docs/api-ingestion.md) | `false` | Clés d'intégration Iris (`integration_credentials`, SHA-256 + scopes), dans le code ; **aucun CORS** | **Déployée, vérifiée bout en bout (18 scénarios HTTP)** |
| **`request-assistant`** | Assistant IA d'instruction. Deux modes : `{request_id, messages}` (contexte de la demande, droit d'**instruction**) et `{organization_id, socle_procedure_id, messages}` (guichet, **démarche seule**, droit de création). Le prompt système, le contexte et la base de connaissances sont composés CÔTÉ SERVEUR ; l'historique renvoyé par le navigateur est une entrée non fiable (`role:"system"` refusé). Identité de l'usager **jamais transmise** (le `select` ne la demande pas). ⚠️ **N'appelle pas le fournisseur** : compose le prompt et le confie au guichet `ai-api` du Socle, qui réserve, appelle et solde (2026-08-29). Aucun secret fournisseur ici. | `false` ⚠️ (JWT vérifié **en code**) | JWT agent + `request_right_for(…,'instruction')` ou `has_any_creation_right_for` ; CORS allowlist | **En service** — vérifiée de bout en bout le 2026-08-29 (réponse réelle, 429 avec la date du Socle) |
| **`socle-proxy`** | Relais serveur vers le Socle pour l'UI : `POST /v1/procedures/list`, `/v1/procedures/get` (fiche complète + la **part agent** de `knowledge_base` — consignes, procédures, documents d'aide, liens, FAQ, garde-fous ; `trainingDocuments`/`aiSources`, matière de l'assistant IA, restent au Socle), `/v1/procedures/document-url` (URL signée d'un document d'aide agent, relayée du Socle **après** vérification que le chemin est cité par cette démarche), **`/v1/organizations/root`** (fiche de l'organisation **principale** du tenant — `id`, `name`, `address` : whitelist stricte, ni téléphone ni courriel. La route ne prend **aucun identifiant du navigateur** — c'est `tenant.socleOrgId` —, sans quoi elle serait un lecteur libre du référentiel d'organisations ; ouverte à tout membre, l'adresse d'une mairie étant publique. Ancre la carte des interventions sur le siège), **`/v1/quartiers/list`** (quartiers **avec géométrie** — la SEULE porte par laquelle `geom` franchit la frontière ; 404 du Socle ⇒ `available: false`, pas une erreur), `/v1/contacts/search`, `/v1/contacts/list` (annuaire paginé, seule route qui sait montrer les fiches archivées), `/v1/contacts/match` (homonymes cherchés **automatiquement au fil de la saisie** par le parcours de création), `/v1/contacts/get` (relecture de l'usager d'un brouillon repris), `/v1/contacts/create` et `/v1/contacts/update` (contacts-api uniquement ; l'update est un PATCH partiel, refus du Socle relayés tels quels), **`/v1/ai/usage`** (consommation IA de la collectivité, relayée du guichet `ai-api` — ⚠️ **réservée aux administrateurs par une garde RÉÉCRITE dans la fonction** : la lecture se fait en service role, le RLS qui gardait autrefois les tables d'Iris ne s'applique plus). Réponses **sanitisées par whitelist** (`_shared/sanitize.ts` — jamais d'`internal_notes`) ; périmètre = membre du tenant + racine dans le périmètre **réel** de la clé Socle (introspection mémoïsée). | `false` ⚠️ (JWT vérifié **en code** — la passerelle bloquerait les préflights OPTIONS) | JWT agent + appartenance ; les routes `/v1/contacts/*` exigent en plus au moins un **droit de création** de demande dans le tenant (`user_has_request_right`/`has_any_creation_right_for`, profils de droits — RM-64), `/v1/procedures/*` restent ouvertes à tout membre ; CORS allowlist (`IRIS_APP_URL` + localhost) | **Déployée, vérifiée bout en bout (14 scénarios HTTP)** |
| **`create-request-from-procedure`** | **Création guidée d'une demande** : démarche rechargée depuis Socle (snapshots construits côté serveur — jamais fournis par le navigateur, clé inconnue → 400), organisation destinataire **obligatoire** et vérifiée dans le miroir du tenant (RM-29), validation `requester_config` + `form_schema` + conditions + pièces (moteur pur `_shared/procedureForm.ts`, partagé avec le front via l'alias `@fn`), contact rapproché relu depuis contacts-api, écriture **atomique** via la RPC `create_request_from_procedure` (demande + pièces + événement `request_created_from_procedure`). Les liens `liee_a` vers des demandes proches ne passent PAS par ici : posés ensuite par le navigateur sous RLS. | `false` ⚠️ (JWT vérifié **en code**) | JWT agent + appartenance + **droit de création** sur le couple (organisation destinataire, démarche) — `user_has_request_right` (profils de droits, RM-60) ; CORS allowlist | **Déployée, vérifiée bout en bout (10 scénarios HTTP + parcours navigateur, re-vérifié avec le parcours redessiné le 2026-08-21)** |
| **`admin-users`** | Opérations service_role sur les comptes : `invite_user` (compte créé **sans mot de passe** et non confirmé + `generateLink`), `send_password_reset` (lien envoyé au TITULAIRE), `delete_user`. Tout le reste passe par le RLS. ⚠️ **Aucun mot de passe n'est généré ni affiché à un administrateur** (invariant) : il n'y a ni `create_user` avec mot de passe, ni `set_password`. | `false` ⚠️ (JWT vérifié **en code**) | JWT + `is_platform_admin` ; CORS allowlist | **Déployée** |
| **`sync-socle-referentiel`** | Sync du miroir `socle_organizations` + cache `socle_procedure_cache` (sous-arbre par tenant, soft-delete, journal `sync_runs`, nom du tenant rafraîchi, recalcul `refresh_request_scope_org` du périmètre porteur des droits) — **déclenchée par le cron quotidien OU par le bouton « Synchroniser maintenant »** (motif Clara) : admin plateforme = tous les tenants (zone superadmin), **administrateur de tenant = son seul tenant** (Paramètres › Référentiel, `organization_id` obligatoire, périmètre dérivé de l'appelant — 403/404 sinon) ; réponse synchrone avec compteurs, `counters.triggered_by` (`cron` ou id de l'appelant) et `counters.scope` (`all` ou tenant) | `false` ⚠️ (JWT vérifié **en code**) | `x-cron-secret` === `CRON_SECRET` **ou** JWT (`is_platform_admin`, ou `organization_members.role = administrateur` du tenant demandé) ; CORS allowlist | **Déployée** |
| **`send-request-email`** | **Ce qui part d'Iris vers l'USAGER**, depuis la fiche. Deux modes, deux habilitations : sans `kind`, le **message libre** rédigé par l'agent (droit d'**instruction**) ; `kind: "cloture"`, l'**avis de clôture** composé INTÉGRALEMENT par le serveur à partir de l'état enregistré — le navigateur n'envoie que l'identifiant (droit de **clôture**). C'est parce que le navigateur ne compose rien que l'ouverture à ce droit est sans risque. ⚠️ **Destinataire résolu ici** (fiche Socle relue, snapshot du dépôt en repli) et **chemins de pièces vérifiés** (`{organization_id}/{request_id}/`) : jamais acceptés du navigateur. Le motif de clôture et le corps d'une note interne ne sortent JAMAIS. Envoi **synchrone** — l'envoi EST le geste. Habillé de la **charte de la collectivité** (couleur + logo, `socle-proxy /v1/organizations/{id}/branding` — décoratif, jamais bloquant). | `false` ⚠️ (JWT vérifié **en code**) | JWT agent + `request_right_for(…, 'instruction' \| 'cloture')` selon le mode ; CORS allowlist | **Déployée** (version 6, charte graphique le 2026-08-30) |
| **`notifications-mailer`** | Draine la **boîte d'envoi** des notifications (un événement, une ligne, N canaux) sur cron. ⚠️ **La base est le seul producteur** — triggers `t40_*` `SECURITY DEFINER`, aucune policy d'écriture cliente, jamais de notification pour son propre geste. L'e-mail ne part JAMAIS du déclencheur : « on n'annule pas une affectation parce qu'un serveur de mail tousse ». `notification_preferences` (*fail open*, globales au compte) décide des canaux. Va aux **AGENTS** : ni identité d'usager, ni description, ni corps de note interne. | `false` | Secret cron | **Déployée** |
| **`auth-email-hook`** | Habille **tous** les mails émis par GoTrue lui-même — aujourd'hui le seul parcours concerné est le **mot de passe oublié self-service** (les gestes d'administrateur passent par `generateLink` dans `admin-users`, sans dépendre du hook). ⚠️ **À activer une fois dans le dashboard** (Authentication › Hooks › Send Email) ; sans `AUTH_HOOK_SECRET` la fonction répond 503 et ne devine rien. | `false` ⚠️ (GoTrue n'envoie pas de JWT) | Signature **Standard Webhooks** vérifiée en code (`AUTH_HOOK_SECRET`) | **Déployée** |
| `process-attachment-queue` | Copie asynchrone des pièces (`copy_status: pending` → `copied`) | `false` | Secret cron | À venir (phase 2) |
| `process-webhook-outbox` | Livraison des webhooks signés (outbox `integration_deliveries`) | `false` | Secret cron | À venir (phase 4) |

Conventions de gamme à respecter (motif Socle) :

- Logique pure co-localisée dans `_shared/{dto,validation,serializers,errors,openapi}.ts`,
  **sans dépendance Deno**, testée par vitest (le `include` de `vite.config.ts` couvre déjà
  `supabase/functions/**`).
- Sérialisation sortante par **whitelist stricte** — jamais de `select *` relayé.
- Enveloppe d'erreurs `{ "error": { code, message } }`, messages en français,
  hors périmètre = 404.
- Le déploiement d'une fonction inclut `index.ts` + tout `_shared/*.ts`.
- **Jamais de clé d'un autre projet dans le navigateur** : les secrets inter-projets vivent
  dans les secrets d'edge functions (voir `docs/demarrage.md`).
